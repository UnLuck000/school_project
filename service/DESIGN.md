# Служба StretchBIT и интерфейс без прав: план разделения

## Зачем

До 1.0.x вся программа — один процесс с правами администратора (окно UAC при запуске,
задание автозапуска «наивысшие права»). При этом она читает и пишет то, что может менять любой
процесс пользователя без прав: папку конфигурации в %APPDATA% (`userdata.py`, `ui/settings.py`),
журнал действий с откатом (`recovery/journal.py`), ссылки-папки в cache/logs, переменные
окружения, сторонние DLL. Проверка кода 13.11.2026 закрыла найденные случаи точечно
(`trustseal`, `winacl.admin_only`, `secure_settings.json`, подпись журнала, `datadirs.py`,
`userdata.remove_links`), но класс уязвимостей «процесс без прав влияет на программу с правами»
остаётся, пока в одном процессе живут окно (которым управляет пользователь) и движок (которому
нужны права).

Разделение:

* **Служба Windows** `StretchBITService[-test]` — LocalSystem, автозапуск, работает без входа
  пользователя и после выхода из системы. Свои данные — только в местах, куда пишут лишь
  администраторы и система: папка программы (Program Files), `%ProgramData%\StretchBIT[-test]\service`
  (DACL: SYSTEM и «Администраторы»). Настройки пользователя, его %APPDATA%, переменные окружения
  и файлы в профиле служба не читает как источник доверия.
* **Интерфейс** — `StretchBIT.exe` без прав администратора (без окна UAC при запуске). Всё, что
  требует прав, просит у службы по именованному каналу.

## Что переезжает в службу (по шагам)

| Шаг | Модули | Состояние |
|-----|--------|-----------|
| 1 | защита файлов `monitor.py`, карантин `quarantine.py`, журнал защиты `recovery/threatlog.py`, белый список `scanner/whitelist.py`, автообновление баз `updater.py` (раз в сутки) | **сделано (минимальная версия)** |
| 2 | контроль запуска `scanner/launchguard.py`, защита от стилеров `toolbox/stealerguard.py` — `service/guards.py`; тревога стилера ждёт решения окна (`stealer.decide`: kill / allow / once), без ответа 10 мин — процесс отпускается, находка «подозрительная»; окна нет — служба запускает его в сеансе пользователя (`ServiceCore.wake_window`, `winapi.launch_in_session`); свои процессы программы защиты не трогают (`ownproc.py`) | **сделано** |
| 3 | сервер AMSI (служба регистрирует провайдер сама: `amsi.register`), журнал PowerShell 4104 и его политика (`pslog.policy`) | **сделано** |
| 4 | датчики сети — DNS (ETW) и TLS (WinDivert только свой или из защищённой папки) — в службе (`net.sensors`, события `dns` / `tls`); разбор, таблицы и оповещения остаются в окне (`netmon.SENSORS`); брандмауэр — `firewall.block_ip` / `block_program` / `unblock` | **сделано** |
| 5 | журнал действий службы (её действия: брандмауэр, AMSI, политика PowerShell, VPN, разрешения стилерам) — в её данных; окно показывает оба журнала вместе (`journal.set_remote`, `where = "service"`), отмена записи службы — `journal.undo` (ослабление) | **сделано** |
| 6 | ядра VPN с правами — TUN sing-box + Xray, WireGuard, OpenVPN (`service/vpnhost.py`); системный прокси и «только локальный прокси» (HKCU пользователя, без прав) остаются в окне | **сделано** |
| 7 | центр восстановления, автозапуск, драйверы — **не** операциями канала: отдельный процесс с правами через окно UAC (`service/elevate.py`: `--tool`, `--undo`) | **сделано** |

Ловушки для шифровальщиков (`toolbox/decoys.py`) живут в профиле пользователя и остаются в
интерфейсе; проверка содержимого по событию шифровальщика (`ransom`) приходит от службы.

## Канал `\\.\pipe\sbit-service[-test]`

* Создаёт служба, первый экземпляр — `FILE_FLAG_FIRST_PIPE_INSTANCE` (имя никто не занял до
  неё), режим сообщений, `PIPE_REJECT_REMOTE_CLIENTS`.
* DACL: SYSTEM и «Администраторы» — всё; «Интерактивные» (IU) — чтение/запись **без**
  `FILE_CREATE_PIPE_INSTANCE`: программа пользователя не может встать вторым сервером.
* **Проверка клиента** (служба): PID клиента от ядра (`GetNamedPipeClientProcessId`) → путь
  образа (`QueryFullProcessImageNameW`) должен совпасть с `StretchBIT.exe` этой установки (папка
  закрыта от записи). Чужие программы отключаются сразу, до чтения запроса. Учётная запись и
  «с правами ли» — из маркера клиента (`ImpersonateNamedPipeClient` на уровне
  идентификации → `TokenUser`, `TokenElevation`). Не больше 4 подключений от процесса.
* **Проверка сервера** (интерфейс): клиент открывает канал с `SECURITY_IDENTIFICATION`
  (сервер не может действовать от имени пользователя) и сверяет
  `GetNamedPipeServerProcessId` с PID службы из диспетчера служб (`QueryServiceStatusEx`).
  Иначе — канал занят чужим процессом: интерфейс работает как раньше, без службы.
* Сообщение — JSON в UTF-8: запрос `{"id", "op", "args"}`, ответ
  `{"id", "ok": true, "result"}` или `{"id", "ok": false, "error", "type"}`
  (`type` — FileExistsError, ValueError, PermissionError, NeedAdmin, Refused...). Запрос до 1 МБ,
  ответ до 32 МБ.
* **События** — длинный опрос: `events {since, wait}` ждёт до `wait` с и отдаёт новые события
  кольца (2000 последних) с номерами; `boot` — номер запуска службы (после перезапуска счёт
  заново). Отдельное подключение интерфейса для событий, отдельное — для запросов.

### Права операций (`service/protocol.py`, OPS)

| Уровень | Кто | Операции |
|---------|-----|----------|
| read | любой проверенный клиент | hello, status, events, quarantine.list, threats.list/get, whitelist.list |
| control | любой проверенный клиент | protection.set (включить, добавить свои папки), bases.reload, quarantine.add, quarantine.delete, threats.add/set_status/mark_path/dismiss, whitelist.remove |
| weaken | проверенный клиент; при запрете (`lock_protection`) — только с правами администратора | protection.set (выключить, убрать папки), quarantine.restore, whitelist.add |
| admin | клиент с правами администратора | config.set (запрет выключения защиты) |

### Файлы пользователя — через дескриптор, а не путь

Служба (SYSTEM) никогда не открывает путь, присланный клиентом: иначе ссылка-папка в профиле
превратилась бы в удаление или запись системного файла от имени системы.

* `quarantine.add`: клиент сам открывает файл (`GENERIC_READ | DELETE`, со своими правами) и
  передаёт номер дескриптора; служба копирует его в свой процесс (`DuplicateHandle` из процесса
  клиента), читает, кладёт копию в карантин и удаляет файл через этот же дескриптор
  (`FileDispositionInfo`). Путь для записи — `GetFinalPathNameByHandleW`.
* `quarantine.restore`: клиент создаёт файл назначения (`CREATE_NEW`, со своими правами) и
  передаёт дескриптор; служба пишет в него содержимое из карантина.
* Автокарантин защиты файлов (совпадение хэша) служба делает сама — как раньше программа с
  правами.

## Установка и удаление

* `installer.iss`: перед заменой файлов — `net stop` службы (ждёт остановки, exe не занят);
  после icacls — `StretchBIT.exe --service-install` (создать или обновить, описание, перезапуск
  при сбое 5/10/30 с, автозапуск, запуск). Деинсталлятор: шаги `--uninstall --silent` (их первым
  делом остановка, затем удаление службы), на крайний случай `sc delete`.
* `uninstall.py`: «Закрыть запущенную программу» сначала останавливает службу (иначе диспетчер
  служб перезапустил бы убитый процесс), «Удалить службу защиты» — `DeleteService`.
* Команды (только с правами администратора): `--service-install`, `--service-remove`,
  `--service-stop`; `--service` — точка входа для диспетчера служб.

## Переходный период

* Из исходников (`python gui.py`) и без установленной службы всё работает как раньше: один
  процесс, окно UAC, защита в самом окне.
* Для разработки: `python -m service --console` — то же ядро службы в консоли (данные в
  `cache/service-dev`); `python gui.py` подключается к нему, если задана переменная
  `STRETCHBIT_SERVICE_DEV=1` (только из исходников; сервер сверяется по пути интерпретатора).
* Служба есть и отвечает → интерфейс запускается без UAC; защита файлов, карантин, журнал
  защиты и белый список — через канал (подмена в `quarantine`, `recovery.threatlog`,
  `scanner.whitelist`: `set_remote`). Остальное (контроль запуска, стилеры, AMSI, сеть, VPN,
  инструменты) пока в интерфейсе и без прав работает в упрощённом режиме; для них есть
  «Перезапустить с правами администратора».

## Известные ограничения минимальной версии

* События защиты (пути файлов) видят все вошедшие пользователи, у которых открыт интерфейс.
* Вредонос в сеансе пользователя может внедриться в процесс интерфейса и слать запросы от его
  имени: служба этого не отличит. Защита — запрет `lock_protection` (ослабляющие операции только
  с правами администратора).
* Проверка файлов в службе идёт в её процессе (как раньше защита файлов в окне), без рабочих
  процессов `scanner.pool`.

## Шаги 2–7: как сделано

* **Защиты** (`service/guards.py`, GuardHost) запускаются вместе с защитой файлов службы, каждая —
  по `config.json` → `guards` (окно передаёт свои галочки `guards.set`; выключение — WEAKEN).
  Находки контроля запуска, AMSI и 4104 служба пишет в журнал защиты сама (сводка по процессу —
  из её `STORY`), окну — событие `guard` со сведениями и `logged: true`: окно их только
  показывает. Сведения переводятся в JSON (`jsonable`).
* **Сеть**: только источники с правами — в службе. События `dns` (DnsQuery) и `tls` (TlsEvent)
  идут в поток EventPump окна и сразу в `RemoteSensor` (`service/remote.py` `dispatch`), минуя
  главный поток. Папку WinDivert из окна служба не берёт.
* **VPN** (`service/vpnhost.py`): окно присылает профиль, настройки `SETTINGS` и готовые
  параметры маршрутизации (`window_options`). Служба — SYSTEM, поэтому: ядра — только свои из
  vpn/bin; в .ovpn запрещены скрипты, плагины, журнал/управление и пути к файлам (только
  встроенные блоки), в .conf WireGuard — PreUp/PostUp/PreDown/PostDown; geo-файлы копируются
  к себе (*.dat, ≤ 256 МБ); ключи параметров — по списку. Подключение переживает перезапуск окна
  (`VpnWindow._adopt_service_vpn`), после сбоя службы kill switch и DNS возвращаются при её
  запуске (`ServiceCore._recover_vpn`).
* **Почему шаг 7 не через канал.** Всё, что окно без прав может попросить у службы, может
  попросить и вредонос в сеансе пользователя (внедрение в процесс без прав не требует прав).
  Защита это выдерживает (операции узкие, ослабляющие — под `lock_protection`), а удаление
  произвольных ключей реестра, служб и файлов из инструментов — нет: это было бы готовое
  повышение прав. Поэтому окно без прав открывает такие инструменты отдельным процессом с
  правами через UAC (`StretchBIT.exe --tool recovery|autoruns|drivers [--tab N]`), а отмену
  записи журнала, которой не хватило прав, — `--undo id...`. Процесс с правами — та же учётная
  запись (тот же %APPDATA%) и подключается к службе сам. UAC отклонили — инструмент
  открывается в окне без прав (только просмотр), как раньше.

## Известные ограничения (после шагов 2–7)

* Окно UAC запрашивает учётную запись администратора: если её вводит другой человек (обычная
  учётная запись), процесс `--tool`/`--undo` работает с его профилем, а не с вашим.
* Сводка по процессу (`processmanager/story.py`) в окне не видит запусков процессов — их видит
  служба (`story.get` отдаёт её сводку, в журнал защиты она попадает сама).
* Свои дочерние процессы окна (PowerShell программы) служба проверяет как чужие (AMSI, 4104).
